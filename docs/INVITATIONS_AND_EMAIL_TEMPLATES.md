# Account invitations and e-mail templates

Status: **ACTIVE** (activated 2026-11-12). `sanitize-html` is installed, the migration has run on the local database, both modules are registered in `AppModule`, and the API and web builds, the unit tests and an end-to-end run (real HTTP against a throw-away copy of the database, a local mail-capture server and a real browser) have passed — §3 records what was done and what each environment still needs.

## 1. What it is

One invitation mechanism for **staff** and **customers**, with their roles and permissions kept entirely apart, plus an **Email Templates** module for the messages it sends.

| Piece | Where |
|---|---|
| Invitation module (API) | `src/modules/account-invitation/` |
| E-mail template module (API) | `src/modules/email-template/` |
| Migration (creates the two tables) | `src/migrations/1795600000000-CreateAccountInvitationsAndEmailTemplates.ts` |
| Customer seam | `src/modules/customer/customer-invitation.port.ts`, `customer.service.ts` |
| Console pages (web) | Internal Administration > **Invitations** (`/platform/internal/invitations`), Platform Settings > **Email Templates** (`/platform/settings/email-templates`) |
| Public page (web) | `/accept-invitation` |
| Staff wizard | third option **Send email invitation** next to the two existing password options (unchanged) |

### Flows
**Staff.** An administrator picks *Send email invitation* in Create User. The account is created through the same `UserService.create` (same role-grant limits and uniqueness checks) **inactive and without a password**, an invitation is stored (only the SHA-256 of a 32-byte token) and e-mailed. The owner opens the link, chooses a password, the account becomes active. The two existing options (autogenerated / custom temporary password, then `force-password-change`) are untouched and remain the fallback when SMTP is not configured. **Staff invitations are `SUPER_ADMIN`-only.** The Users permission codes (`CREATE_USER`, `EDIT_USER`, `VIEW_USER`, `RESET_USER_PASSWORD`) are already withheld by the server from every other role (`administration-permissions.ts`), and the service checks the caller's role as well (`assertSuperAdmin`) for creating, sending, re-sending, cancelling and listing staff invitations — so the rule does not depend on how those codes are granted. Sending or re-sending a link to an **existing** staff account additionally needs `EDIT_USER` **and** `RESET_USER_PASSWORD` (plus the assignment boundary): it hands the link's holder the right to choose that account's password, so it is treated as the password reset it is. **Customer invitations** follow the business customer permissions: `EDIT_CUSTOMER` to re-send or cancel (also through the Customers screen's own "resend activation"), `VIEW_CUSTOMER` to list.

**Customers.** There is no direct Create Customer screen: customers still come from registration and approval. On approval the customer's activation e-mail becomes an invitation. When the approval also raises a Security Deposit, the message is the managed **Customer Invitation (Security Deposit)** template (`CUSTOMER_DEPOSIT_INVITATION`): the same link, plus the customer reference, the amount (written exactly as before, e.g. `AED 1,000.00`) and the fact that the account activates once the payment is verified — everything the old fixed message said. The deposit message is also what a re-send uses, since the payment is still due. Activation links issued the old way keep working until they expire (`POST /customers/activate` is unchanged); re-sending withdraws any unused old link. With the module off, the old fixed deposit message is sent exactly as before. A customer who sets a password while a deposit is still due stays `INACTIVE` (same rule as the old link): the acceptance answers `accountActive: false`, the page then says "Your password is set — sign in to complete your Security Deposit payment" instead of "Your account is ready", and the "Account Activated" e-mail is not sent.

A customer is **waiting for setup** — and so can be invited, can open a link and can be re-sent one — when the account is `INACTIVE` (never activated, or password set and deposit still pending), or `ACTIVE` with **no password** (a verified deposit activates an account even if its owner never opened the link). An `OVERDUE` customer is a billing suspension that setting up an account must never lift, and an `ACTIVE` customer with a password is already set up: for both, `CustomerService` keeps sending the activation e-mail exactly as it always has (it asks the invitation module first, `canIssueForCustomer`).

### The messages, their design and the branding
Six managed messages, each in English and Arabic (twelve templates): Staff Invitation, Customer Invitation, Customer Invitation (Security Deposit), Invitation Resent, Invitation Expired, Account Activated. Each is a heading, a greeting, the message, a details panel (account, invited by, link expiry — and for the deposit message the reference, the amount and the account status), a call-to-action button, the link again as copyable text, and a short note; the expired message has no button because its link is dead. They sit in one responsive layout (a fluid card of at most 600 px, tables and inline styles only, so mail clients render it): a brand header, the message, a footer. Arabic messages are laid out right to left throughout and avoid letter-spacing and capitals, which break Arabic letters apart. They are built from one composer in `default-templates.ts`, so the two languages cannot drift apart structurally.

The administrator controls the brand on Email Templates > E-mail settings: **company name**, **logo** (an https address recipients' mail programs can load — it is not uploaded or stored; with none, the header shows the company's initial and name), **header colour** (the name on it turns black or white, whichever reads better), **primary button colour** (the label is white, so a colour too light for it — under 4.5:1 contrast — is refused; the default `#185FA5` is about 6.5:1) and a **footer sentence per language** (the built-in sentence is used when empty). Each is a SYSTEM attribute row created the first time it is saved, and every stored value is validated again when read (the Attributes screen can edit these rows too), so an invalid one falls back to the default and can never break or inject into a message. The button colour reaches the template through `bgcolor="{{buttonColor}}"`; `{{companyName}}` and `{{buttonColor}}` are always the branding's. Preview and the test e-mail use the saved branding.

**Custom templates** an administrator creates are drafts: no workflow sends them (only the built-in keys are ever rendered), and the screens say so — they carry a "Custom" badge and "Not sent by any workflow", have no Active switch, and the editor shows a notice. Preview and the test e-mail to yourself work for them. Giving a custom template a real workflow would be a separate piece of work.

**Language.** The invitation e-mail is written in the invitee's language: for staff, chosen in the Create User wizard (*Invitation language*; it is saved as the new user's own language, so the e-mail, the acceptance page and the user's first sign-in agree; left out it is English) and for customers, the language on their registration. The public acceptance page opens in that same language (the link check reports it), right to left for Arabic, and the visitor can switch it. The Create User wizard itself is shown in the signed-in administrator's language and direction.

### Statuses
`PENDING`, `ACCEPTED`, `EXPIRED`, `CANCELLED`. One row per account; resending re-opens it with a new token and a new 24-hour expiry.

### Security properties (all in `account-invitation.service.ts`)
Token 32 random bytes, only its hash stored, never logged or audited · 24 h expiry stamped and compared with the **database** clock · acceptance is one atomic conditional `UPDATE … WHERE status='PENDING' AND expires_at > NOW(6)` · resend replaces the token (the earlier link dies) · acceptance re-checks the account under a row lock (still waiting for setup, same e-mail) and otherwise cancels the invitation · accepting ends every existing session of the account (a first-time invitee has none) · the request carries only a token and a password, so roles can never be influenced at acceptance · every refusal of a public link reads the same · staff resend/cancel apply the super-administrator rule (`assertActorMayModifyUser`) and the assignment boundary (`assertActorMayTakeOverAccount`), and re-sending to an existing staff account needs `RESET_USER_PASSWORD` too · cooldown (60 s) and cap (20 sends of a live invitation) are checked **inside the transaction that holds the account's row lock**, and the attempt time is stamped in that same transaction, so parallel requests take turns instead of slipping past; only a message that really went out counts towards the cap, and re-opening an accepted, cancelled or expired invitation starts a new round · 60 invitations/hour per administrator (counted for every first invitation, however the account was made; the count is of invitations created in that hour whose `created_by` — "last issued by" — is that administrator, so a re-send by someone else moves the row to them), strict per-IP limits on the public routes · audit rows for create, resend, accept, expire, cancel and failed delivery · a failed delivery's stored/logged/returned reason has any link or 64-character token removed (some mail gateways quote the rejected message) · a pending invitation is cancelled automatically when its account's e-mail changes, a staff account is activated/deactivated, or either kind is deleted (`account-invitation.subscriber.ts`) · every transaction takes the account row first and the invitation row second, and no locking read is made of an invitation row that may not exist yet (that would take an InnoDB gap lock and deadlock concurrent first invitations) · links are built from `STAFF_PORTAL_URL` / `CUSTOMER_PORTAL_URL` only (never the request), and must be https in production · on the web, the public acceptance page is `no-referrer`/`noindex`, its token query is never cached once the page is left (`gcTime: 0`), the token and password are dropped from the mutation cache as soon as the page lets go, a failed link check that is not a 400 (server error, network, rate limit) is never reported as "invalid link", and the address of a token-carrying page (`/accept-invitation`, `/activate`) is never copied into `/login?returnUrl=` when a session ends while it is open (`isSafeReturnUrl`).

E-mail templates: managed by `SUPER_ADMIN` only; HTML is sanitised on save, preview and test-send (styles: no `url()`, `expression()`, `javascript:`, `@import` or backslash escapes, line breaks included); every placeholder value is HTML-escaped (and stripped of line breaks in the subject and text); test e-mails go only to the signed-in administrator; a missing or switched-off template falls back to the built-in default so an invitation can never be blocked. Bodies are stored as `MEDIUMTEXT` (a `TEXT` column holds only 65,535 bytes, less than the accepted body size).

## 2. How it is wired

* `AppModule` imports `EmailTemplateModule` and `AccountInvitationModule`. Both register their entities through `TypeOrmModule.forFeature` (the app uses `autoLoadEntities`). The entities and the migration are kept identical on purpose — TypeORM's own schema comparison reports **0** pending changes for the two tables after the migration, so `synchronize` (development only) never alters them.
* The migration `1795600000000` creates `account_invitations` and `email_templates` and nothing else: no column, row or key of any existing table changes (checked by comparing every column, index and foreign key of the whole database before and after). It is idempotent, and `down()` refuses to drop a table that holds rows.
* `sanitize-html` (exact version 2.17.5, the newest that supports Node 20; later versions require Node 22) is loaded lazily (`html-sanitizer.ts`): if the package were ever missing, saving/previewing template HTML answers 503 with a clear message, while the built-in templates and invitations still work.
* The web screens ask the server whether the feature exists (`GET /account-invitations/capability`, `GET /email-templates/meta`). A server **without** the modules (an older API) answers 404; the screens then say "not switched on yet", the wizard offers only its two password options and the user page shows no invitation card.
* `CustomerService` finds the invitation module by token at send time (`ModuleRef`); without it the customer activation e-mail goes out exactly as before, and for the customers the module must not touch (see above) it still does.
* `src/config/data-source.ts` (the TypeORM CLI) globs every `*.entity.ts`, so `npm run migration:generate` now sees the two entities as part of the schema — correct, since they are.

A leftover table named `user_invitations` (from the paused SaaS experiment) may exist in a developer database with a different shape. This feature uses `account_invitations` and never touches it.

## 3. Activation record and what each environment needs

**Done on the local development database (`ccb`) on 2026-11-12:** the database was checked first (neither table existed; the migration history had only this migration pending); `sanitize-html@2.17.5` and `@types/sanitize-html` were installed; the migration was moved to `src/migrations/` and ran on the API's next start (migration id 70); both modules were registered; the twelve built-in templates were written at that start. Database change: **2 tables added, nothing else** (72 → 74 tables; every column, index and foreign key of the other 72 is identical before and after).

**For any other environment (DEV server, UAT, production):**

1. Deploy the code and run `npm ci` (this installs `sanitize-html`; Node 20 or newer).
2. Configure (see `.env.example`): `STAFF_PORTAL_URL` (or `CUSTOMER_PORTAL_URL`; **https in production**), `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`; optionally `COMPANY_NAME` (or set it in Email Templates > E-mail settings). Without SMTP the capability endpoint reports `emailConfigured: false` and the wizard keeps its two password options as the fallback.
3. Start the API. With `DB_MIGRATIONS_RUN` on (the default) the migration creates the two tables on that start; where the API's database account may not create tables, run `npm run migration:run` with the migration account instead. `synchronize` is never needed (and is refused outside development). Back up the database first, as for any release.
4. On that start `EmailTemplateService` writes the twelve built-in templates that are not stored yet and never overwrites an edited one.
5. Sign in as SUPER_ADMIN and set the brand in Email Templates > E-mail settings (company name, logo address, colours, footer sentences); send yourself a test e-mail.

Rollback: remove the two modules from `AppModule` and restart. The tables stay (drop them by hand only if empty — `down()` refuses otherwise). Existing users, customers and links are unaffected.

## 4. Not covered / decisions left

* No in-app notification to the inviting administrator exists in this codebase, so an expired invitation notifies the invitee only; the Invitations screen shows the status.
* A customer's `INACTIVE` status also means "not yet activated", so customers are cancelled on e-mail change and delete, not on "deactivation".
* The Customers screen's own "resend activation e-mail" (`CustomerService.resendActivationEmail`, unchanged) still refuses an `ACTIVE` customer, so for an `ACTIVE` customer who never set a password the way to send a new link is the Invitations screen (or the invitation already sent). An `OVERDUE` customer is not invited by this module at all; it keeps the legacy activation e-mail.
* The failed-delivery text is stored without links or tokens, but it can still hold other server detail (for example an SMTP reply). It is shown only to holders of `VIEW_USER` / `VIEW_CUSTOMER`.
* Customer e-mail is not unique in the database and has no duplicate check; this feature does not add one.
* The logo is an address, not an uploaded file. The files this application stores (registration documents) are private records behind sign-in, while a logo in an e-mail must load for anyone's mail program without signing in — so it is an image you host (your website or a CDN), and a `data:` image would not display in most mail programs. Serving an uploaded logo from the API would need a new public route and a storage decision, so it was left out. The address must stay reachable from the internet, or recipients see a broken image.
* The Create User wizard's CSV download keeps English column labels (it is a file for other tools), and the sign-in and activation pages (not part of this work) are still English-only.
* A staff account that is waiting for setup but has **no invitation row** (for example one created inactive without a password through the plain Create User API, or one whose invitation failed halfway) has no "Send invitation" button on its page: the API route exists (`POST /account-invitations/staff/:userId/send`) and the Invitations screen lists every invitation that does exist.
* Existing behaviour, not changed here: creating several users at the very same instant (`POST /users` in parallel) can answer 409 "The request conflicted with another change. Please try again." because of lock contention in the existing create-user transaction; the same happens with and without invitations, and a retry succeeds. The existing person-name rule accepts markup characters; every e-mail this feature sends escapes names, so they appear as inert text.
* Arabic wording was written for this release and has not been reviewed by a native speaker.
* Email-template HTML is edited as source (no rich-text editor in the project).
